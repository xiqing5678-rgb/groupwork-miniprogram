# GroupWork 需求文档（PRD 摘要）

> 本文档描述已实现的功能与关键规则，用于说明「为什么这样设计」，不是事后补写的立项书。

## 1. 背景与问题

课程小组作业的分工普遍依赖微信群口头协商，导致三类问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| 分工不公 | 任务由组长指派，难度与工作量分配随意 | 成员积极性下降 |
| 进度不可见 | 只能靠追问「你做到哪了」 | 临期才发现没人做 |
| 责任不可回溯 | 出问题后各说各话 | 沟通成本上升 |

## 2. 目标用户与角色

| 角色 | 诉求 |
|---|---|
| 组长 | 快速建组、发布任务、掌握进度、必要时兜底指派 |
| 组员 | 看到任务全貌、自主认领、明确自己的截止时间 |

## 3. 核心流程

```
创建小组 → 生成邀请码 → 组员加入 → 组长/组员发布任务
        → 成员认领 或 组长指派 → 提交 → 进度更新 → 结束小组
```

## 4. 用户故事

| 编号 | 角色 | 故事 | 验收标准 |
|---|---|---|---|
| US-01 | 组长 | 我想创建一个小组并生成邀请码 | 创建后可见邀请码，他人凭码加入 |
| US-02 | 组员 | 我想凭邀请码加入小组 | 加入后出现在成员列表，可看到任务 |
| US-03 | 任意成员 | 我想发布一个带截止时间的任务 | 任务出现在列表，状态为「待认领」 |
| US-04 | 组员 | 我想自己认领任务 | 认领后任务归属为我，其他人不可重复认领 |
| US-05 | 组长 | 我想把没人接的任务指派给某人 | 指派后归属变更，并记录操作日志 |
| US-06 | 组员 | 我想提交已完成的任务 | 状态变为「已提交」，进度看板同步更新 |
| US-07 | 任意成员 | 我想看到每个人的任务与完成率 | 进度页按成员聚合展示 |
| US-08 | 组长 | 我想约定组会时间 | 时间对所有成员可见 |

## 5. 异常流程

| 场景 | 处理 |
|---|---|
| 重复认领同一任务 | 云函数以任务状态为准，第二次认领返回失败提示 |
| 邀请码无效 / 小组已结束 | 拒绝加入，提示原因 |
| 任务已逾期仍未提交 | 进度看板标记「逾期」，不自动关闭任务 |
| 组员退出后仍有未完成任务 | 任务回到「待认领」，由组长重新指派 |
| 非组长尝试结束小组 | 云函数校验角色，拒绝操作 |

## 6. 数据埋点

| 事件 | 触发时机 | 用途 |
|---|---|---|
| `group_create` | 创建小组成功 | 统计建组量 |
| `group_join` | 成功加入小组 | 衡量邀请转化 |
| `task_create` | 发布任务 | 任务密度 |
| `task_claim` | 认领成功 | 自主协作比例 |
| `task_assign` | 组长指派 | 兜底指派比例（对照认领率） |
| `task_submit` | 提交任务 | 完成率 |
| `group_end` | 结束小组 | 生命周期长度 |

> 埋点字段：`event` · `groupId` · `userId` · `timestamp` · `payload`

## 7. 非功能要求

- **权限**：客户端不可直接读写数据库，安全规则全部关闭，仅云函数可用。
- **数据量**：单小组 ≤ 20 人、任务 ≤ 200 条，当前实现按此规模设计。
- **性能**：进度页聚合查询需在 1 秒内返回。
